# 검색 품질 평가와 평가 에이전트 진행 계획

상태: 1차 점검 완료(Issue #39), 평가 도구는 계획(미구현). 이 문서는 청킹·검색을 바꿀 때 "전후 검색 결과 비교"를 반복 가능한 절차로 만들기 위한 진행 순서를 적는다.

## 1차 점검 결과 (Issue #39, 2026-11-17)
적재 절차와 검색 결과를 기록한다. 골든 셋이 아니라 사람이 읽고 매긴 1차 점검이다.

### 적재
- DB: 이 1차 점검은 공용 로컬 DB(`moeun`)에서 했다. 이후 재적재·검색 점검은 임시 DB로만 한다. `DATABASE_URL` 환경변수로 DB를 고른다(`.env`보다 우선). 임시 DB는 `docker exec moeun-postgres psql -U moeun -d postgres -c "CREATE DATABASE moeun_ragcheck"` 후 `backend/src/main/resources/db/schema.sql`을 적용해 만든다.
- 명령: `scripts/ingest/ingest.sh` (PDF를 `docs/raw/`에 받고 `moeun-ingest`로 적재. `scripts/ingest/allowlist.yml`에 없는 자료는 거부)
- 자료: 삼성자산운용 KODEX 미국S&P500 투자설명서(137청크), 미래에셋자산운용 TIGER 미국S&P500 투자설명서(141청크). `rag_document` 2행, 둘 다 `is_active`.
- 재실행: 같은 명령을 다시 돌리면 두 건 모두 "같은 내용의 문서가 이미 있습니다. 건너뜁니다"가 나오고 문서·청크 수가 그대로다(수용 기준 2). 다만 임베딩은 DB 확인 전에 만들어져 재실행마다 소액의 임베딩 비용이 든다.
- 허락 없는 자료: 허락 목록 항목(URL·운용사·유형)과 본문 `content_sha256`을 확인하려고 로컬 파일은 읽지만, 목록에 없거나 해시가 다르면 임베딩·DB 연결 전에 거부한다(`tests/test_rag_search.py`, 수용 기준 3).

- 요약: 11개 중 적중 5, 미흡 5, 근거 없음 1. 모든 질문에서 운용사 2곳이 섞였다(FR-AI-03). ‘ETF 위험’(수용 기준 1)은 위 표대로 두 운용사가 상위 5개에 섞여 나온다.
- 미흡한 질문(환율 위험, 수수료·보수, 원금 보장, 세금)은 구어체 질문이 문서의 문어체 표현과 멀어서일 가능성이 있다. 같은 주제를 문서 용어로 물은 질문 3(환헤지)은 적중했다. 확정하려면 골든 셋으로 재측정해야 한다.
- 위 "기준 점수를 재면 드러날 것" 4가지 중 청크에 제목 맥락이 없는 점이 결과에서 보인다. 삼성 청크는 앞에 문서 제목이 없어 본문만으로 출처를 알 수 없고, 수익률·재무제표 표 청크가 거리 0.5대로 올라온다.
- "근거 없음" 임계값 자료: 무관한 질문(11번)의 1위 distance는 0.777, 관련 질문의 1위는 0.40~0.65(8번 상장폐지 0.653이 가장 멀다). 임계값은 0.75 안팎이 후보이나 표본이 작아 정하지 않는다.
- 이 점검은 평가 도구 없이 한 것이다. 후속: 위 질문을 `tests/eval/golden.jsonl`로 옮기는 PR 1(아래 진행 순서).

## 왜 필요한가
- `.claude/rules/rag.md`는 청킹 규칙을 바꾸면 바꾼 이유와 검색 결과 비교를 PR에 남기라고 요구한다. 지금은 비교할 도구도 기준 질문도 없다.
- `.claude/rules/testing.md`는 청킹·검색 로직을 바꾸면 대표 재질문 → 기대 청크 케이스를 추가하라고 요구한다. 지금 테스트는 청크 길이와 `diversify_orgs`만 본다.
- 기성 에이전트(wshobson, VoltAgent)에는 이 프로젝트의 불변 조건(청크 UPDATE 금지, 운용사 2곳, 재질문 → 독립 질의)을 아는 평가 에이전트가 없다. 직접 만든다.

## 만들 것 세 가지
에이전트부터 만들지 않는다. 에이전트는 아래 1, 2가 있어야 할 일이 생긴다.

| 순서 | 산출물 | 위치 | 네트워크 |
|---|---|---|---|
| 1 | 기준 질문 세트(골든 셋) | `tests/eval/golden.jsonl` | 없음 |
| 2 | 평가 실행기 | `app/eval/`(CLI `moeun-eval`) | DB, OpenAI |
| 3 | 평가 에이전트 | `.claude/agents/rag-evaluator.md` | 실행기를 호출 |

## 1단계: 골든 셋
한 줄이 질문 하나다.

```json
{"id": "risk-01", "query": "S&P500 ETF 환율 위험이 뭐야?", "doc_type": "DISCLOSURE", "expect": [{"source_url": "https://...", "phrase": "환율 변동에 따라"}], "min_orgs": 2}
```

- **기대 청크는 `chunk_id`로 적지 않는다.** 재적재하면 `chunk_id`가 바뀐다. `source_url` + 그 청크에 들어 있어야 할 문구(`phrase`)로 적는다. 검색된 청크의 `content`에 문구가 있으면 적중이다.
- `query`는 독립 질의로 적는다(재질문 → 독립 질의 변환은 LLM 단계라 따로 평가한다. 아래 "범위 밖" 참고).
- 실제 사용자가 쓸 법한 짧은 구어체로 쓴다. 문서 문장을 그대로 베끼면 점수가 부풀려진다.
- 처음에는 20~30개로 시작한다. 구성: 교육자료(EDU) 절반, 공시(DISCLOSURE) 절반, 답이 문서에 없는 질문 3~5개(`expect: []`, 근거 없음을 확인).
- 검색 실패를 발견할 때마다 그 질문을 추가한다. 골든 셋은 PR로만 바꾼다.

결정할 것: 골든 셋에는 문서 문구가 일부 들어간다. `docs/raw/`를 git에서 뺀 이유(저작권)와 충돌하지 않는지 확인하고, 문구는 한 구절 이내로 짧게 유지한다.

## 2단계: 평가 실행기
`moeun-eval --golden tests/eval/golden.jsonl --out result.json`

- 골든 셋의 각 질문을 실제 `Retriever.search`로 돌린다(운영 코드와 같은 경로, 같은 SQL).
- 지표
  - `hit@k`: 상위 k개 안에 기대 문구가 든 청크가 있는 질문의 비율(k = `RAG_TOP_K`).
  - `MRR`: 첫 적중 청크 순위의 역수 평균.
  - 공시 질문의 운용사 수 ≥ `min_orgs` 충족 비율(FR-AI-03).
  - 답 없는 질문에서 상위 1위의 `distance`(나중에 "근거 없음" 임계값을 정할 자료).
- 출력: 질문별 결과 JSON과, PR에 붙일 마크다운 표. `--compare before.json after.json`은 지표 차이와 좋아진·나빠진 질문 목록을 낸다.
- 지표는 검색 품질 수치다. 금액·수익률 계산이 아니므로 절대 원칙 1과 무관하다.
- pytest에 넣지 않는다(테스트는 네트워크 금지). pytest에는 실행기의 순수 함수(적중 판정, 지표 계산, 비교)만 fake 데이터로 테스트한다.
- `/health` 외 엔드포인트를 새로 만들지 않는다. CLI로만 둔다.

### 전후 비교를 위한 DB
운영·공용 DB에서 비교하지 않는다. 임시 DB를 쓴다.

1. `pgvector/pgvector:pg16` 컨테이너를 띄우고 `../db/erd.md`의 DDL을 실행한다.
2. 기준 브랜치(develop) 코드로 평가용 문서를 적재 → `moeun-eval --out before.json`.
3. DB를 비우고, 작업 브랜치 코드로 같은 문서를 적재 → `moeun-eval --out after.json`.
4. `moeun-eval --compare before.json after.json` 결과를 PR에 붙인다.

임시 DB를 쓰는 이유: 전후 비교는 실험이다. 운영 DB에 `--rechunk`를 하면 그 순간 검색 결과가 바뀌므로, 비교로 개선을 확인한 뒤에만 운영 DB에 재적재한다.

## 3단계: 평가 에이전트 `rag-evaluator`
- 역할: 청킹·검색 변경에 대해 위 4단계 절차를 실행하고 전후 비교 보고서를 쓴다. 코드는 고치지 않는다.
- 도구: `Read, Grep, Glob, Bash`.
- 본문에 넣을 것
  - `.claude/rules/rag.md`와 이 문서를 먼저 읽는다.
  - `git diff develop...HEAD -- app/rag app/ingest`로 무엇이 바뀌었는지 확인한다.
  - 임시 DB에서만 적재·평가한다. `.env`와 `docs/raw/`는 읽지 않는다(`settings.json`의 deny). 평가용 문서 경로와 DB 접속 정보는 호출자가 준다.
  - 출력: 지표 표(전 / 후 / 차이), 나빠진 질문 목록과 각 질문에서 전후로 검색된 청크, 결론 한 줄(개선 / 악화 / 차이 없음). 골든 셋에 없는 실패를 봤으면 추가할 질문을 제안한다.
- 짝이 되는 에이전트: 고치는 쪽은 `vector-database-engineer`, 측정하는 쪽은 `rag-evaluator`. 고친 사람이 스스로 채점하지 않게 나눈다.
- 반복 절차가 굳으면 `.claude/skills/eval-retrieval/`로 스킬도 만든다.

## 진행 순서와 PR 단위
1. **PR 1**: 골든 셋 20~30개 + 적중 판정·지표 계산 순수 함수와 테스트. (적재 문서가 정해져야 시작할 수 있다.)
2. **PR 2**: `moeun-eval` CLI와 임시 DB 절차(README에 명령 추가). 현재 코드의 기준 점수를 이 PR에 기록한다.
3. **PR 3**: `rag-evaluator` 에이전트, `CLAUDE.md` 팀 설정에 한 줄 추가.
4. 이후 청킹·검색 PR은 전후 비교 표를 붙인다.

## 먼저 정해야 할 것
- **평가용 문서**: `../../docs/rag-sources.md`(Issue #24)에 후보를 정리했다(2026-11-17 팀 승인, Issue #39). 공시(DISCLOSURE) 투자설명서 2건(삼성자산운용 KODEX 미국S&P500, 미래에셋자산운용 TIGER 미국S&P500)이라 운용사 2곳 조건(FR-AI-03)을 평가할 수 있다. 그 문서의 이용 허락은 "허용(간주)"였고 팀 승인을 받았다(FR-AI-10). 허락 목록은 `scripts/ingest/allowlist.yml`이다. 교육자료(EDU)는 허락이 불확실해 아직 없으므로, 위 골든 셋의 "교육자료 절반" 구성은 EDU 자료가 정해질 때까지 공시 질문과 "답이 문서에 없는 질문"으로 채운다.
- **재청킹 방식**: 운영 DB 재적재는 `moeun-ingest --rechunk`로 한다(스키마 변경 없음). 동작과 정합성 규칙은 `../db/erd.md` §5-E, `chunk_no`의 의미는 `../db/tables.md` §11에 적혀 있다.
- **임베딩 비용**: 평가 한 번에 문서 전체를 두 번 임베딩한다. 평가용 문서를 작게 유지하거나 임베딩 캐시(내용 해시 → 벡터 파일)를 실행기에 둔다.

## 기준 점수를 재면 바로 드러날 것으로 보이는 차이
코드를 읽고 찾은 규칙과 구현의 차이다. 아직 측정하지 않았다. 골든 셋의 첫 번째 쓸모는 이것들의 영향을 재는 것이다.

- `split_chunks`는 청크 앞에 문서 제목·소제목을 붙이지 않는다(`rag.md` 청킹 규칙 3).
- `split_chunks`는 긴 문단을 글자 수로 자른다. 문장 중간에서 잘릴 수 있다(`rag.md` 청킹 규칙 2).
- `Retriever.search`는 `hnsw.ef_search`·`hnsw.iterative_scan`을 설정하지 않는다. `../db/erd.md` Q3은 둘을 전제로 한다. `doc_type` 필터가 걸리면 결과가 `LIMIT`보다 적을 수 있다.
- `diversify_orgs`는 후보(`k * 4`) 안에 두 번째 운용사가 없으면 1곳만 돌려준다. `erd.md` Q3의 "찾은 운용사를 빼고 한 번 더" 재검색이 없다.

## 범위 밖(다음 단계)
- 재질문 → 독립 질의 변환 품질, 답변의 근거 충실도(인용한 청크가 답을 실제로 뒷받침하는가). LLM 호출이 필요한 평가라 검색 평가가 자리 잡은 뒤에 다룬다.
- 리랭커·하이브리드 검색 도입. 기준 점수가 있어야 효과를 판단할 수 있다.
