## 목적

문구표(`copy/copy.ko.yml`)를 **요청마다 여러 번 디스크에서 다시 읽는 구조**를 바꿔서, 문구표가 어디서 한 번 읽히고 어떻게 전달되는지 명확하게 만든다. 성능보다는 "의존성이 보이게 하는 것"이 주목적이다.

## 배경

- `load_copy()`는 부를 때마다 YAML 파일을 읽고, 중복 키·빈 값·필수 키를 검증한다(`app/core/copy.py`).
- 앱 코드에서 `load_copy()`가 10곳 넘게 불린다. `agent.py`의 `assemble()` 한 번에도 여러 번 불린다.
- `app/llm/prompts.py`는 import 시점에 `_COPY = load_copy()`를 실행한다. 모듈을 import만 해도 파일을 읽는 부수 효과가 있다.
- 함수들이 문구표를 인자로 받지 않고 직접 읽기 때문에, 함수 시그니처만 봐서는 문구표에 의존한다는 걸 알 수 없다.

## 할 일 (계획 단계에서 둘 중 하나를 고른다)

**A안: 캐시**
- `path`를 주지 않은 호출(기본 경로)만 `functools.cache`로 한 번 읽게 한다. 경로를 명시한 호출(`load_copy(path)`)은 지금처럼 매번 읽는다.
- 변경 범위가 작다.

**B안: 주입**
- `main.py`의 lifespan에서 문구표를 한 번 읽어 `ChatAgent`에 생성자로 넘긴다.
- 문구표가 필요한 함수는 `Copy`를 인자로 받는다.
- 팀 규칙("의존성은 생성자로 주입한다. 전역 싱글턴 금지")에 더 맞지만 변경 범위가 크다. LangGraph 전환 때 노드에 상태로 넘기기도 쉽다.

## 제약

- **동작 변화 없음.** 같은 입력에 같은 문구가 나와야 한다.
- **테스트 파일은 수정하지 않는다.** 테스트는 `load_copy()`를 직접 부르고(`test_out_of_scope.py` 등), `test_copy.py`는 `load_copy(tmp_path ...)`로 임시 문구표를 쓴다. 이 호출들이 그대로 동작해야 한다.
- 환경 변수 `MOEUN_COPY_PATH`로 경로를 바꾸는 기능을 유지한다. A안이면 캐시 키에 경로가 반영되는지 확인한다.
- `prompts.py`의 import 시점 로딩을 없앨지는 계획 단계에서 판단한다. `SYSTEM_PROMPT`가 문구를 품고 있고 테스트가 `SYSTEM_PROMPT`를 import하므로 영향 범위를 먼저 확인한다.
- #3(계약)과 같은 파일을 건드리면 순서대로 진행한다.

## 참고 개념

- **import 시점 부수 효과**: 파이썬은 import할 때 모듈 최상단 코드를 실행한다. 거기서 파일을 읽거나 네트워크를 부르면, import만 해도 일이 일어나고 테스트가 그 순서에 묶인다. 자바의 `static` 초기화 블록에서 I/O를 하는 것과 같은 문제다.
- **`functools.cache`**: 같은 인자로 다시 부르면 저장해 둔 결과를 돌려준다. 이 프로젝트의 `get_settings()`가 이미 `@lru_cache`로 같은 방식을 쓴다.
- **캐시 vs 주입**: 캐시는 "숨은 전역 상태"를 하나 두는 것이고, 주입은 의존성을 생성자·인자로 드러내는 것이다. Spring이 기본으로 하는 게 주입이고, 테스트에서 대역을 넣기도 주입이 쉽다. 대신 시그니처가 늘어난다. 트레이드오프를 PR에서 설명할 수 있으면 좋다.
- **명시적 의존성**: 함수가 무엇에 의존하는지 시그니처에 드러나면, 그 함수를 처음 보는 사람도 영향 범위를 바로 안다. 결합도를 "보이게" 만드는 것도 유지보수 개선이다.
