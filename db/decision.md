# ADR-001. 목표 달성 시뮬레이션 서비스의 DB 모델 채택

- 상태: 확정 (투표 결과에 따라 채택). 스키마는 ADR-002로 축소되었다
- 대상: `requirements/SRS.md` (요구사항 68건), PostgreSQL 16 + pgvector
- 산출물: `final/v1/erd.md`, `final/v1/schema.sql` (테이블 25개, 트리거 6개). 이 ADR 본문의 `final/erd.md`·`final/schema.sql`은 v1 파일을 가리킨다
- 참가 안: A(정합성), B(성능), C(도메인·확장성) — 익명 라벨만 사용

## 1. 배경

내 계획 입력 → 계산 → 3구간 결과 → 대안·비교 → 내 계획 적용·되돌리기 → AI 설명(RAG)으로 이어지는 서비스의 DB를 설계해야 했다. 요구사항에는 아직 확정되지 않은 항목(TBD)이 많아서, 값이 바뀌어도 구조를 바꾸지 않는 설계가 필요했다.

설계 중 진행자가 확정한 해석은 세 가지다. 세 모델러에게 같은 내용을 같은 시점에 전달했다.

1. FR-INP-08: 토글 ON이면 월납입액을 **1개만** 입력받는다.
2. AI 대화 메시지(FR-AI-06/07)는 DB에 **영속 저장**한다.
3. 서버 세션 저장소(NFR-SEC-02)는 DB 모델링 **범위에 포함**한다.

평가 기준은 요구사항 커버리지 30, 무결성·정규화 25, 주요 쿼리 성능 20, 확장성 15, 단순성 10이다.

## 2. 후보안 요약 (최종안 v2 기준)

## 4. 채택 이유 (B v2)

투표서에 나온 근거만 적고, 출처 투표서를 괄호로 표시한다.

- **주요 쿼리 성능이 가장 좋다 (B 18 / A 15.5 / C 13)** (A, C 투표서). 결과 화면이 PK 조회 몇 번과 최대 6행 범위 조회로 끝난다. 월별 그래프는 시나리오 행의 배열 1행을 읽는다. 세션은 폴링이 SELECT만 하고 사용자 조작만 UPDATE한다.
- **쓰기 비용이 낮다** (A 투표서의 C 평가, B 투표서의 A 평가). A는 30년 목표에서 계산 1회에 월별 행 1,083개를 쓰고, C는 run 1건 저장에 검증 함수를 5~6회 실행한다. B는 이 두 부담을 모두 피했다.
- **무결성도 충분히 강하다** (A 투표서). 소유권 복합 FK, 현재 실행 포인터의 복합 FK, 데이터 종류 상수 컬럼 + 복합 FK, 입력 투입값 복사와 원본의 일치 FK를 갖췄다. 무결성 점수는 B 21.5, A 22.0, C 22.5로 격차가 작다.
- **C보다 단순하고 바로 구현할 수 있다** (A 투표서). C는 정책 승인에 필요한 규칙 13행이 있어야만 조건을 저장할 수 있어서, 미결 TBD 값이 확정되기 전에는 동작하지 않는다. 단순성 점수는 B 7.0, A 7.5, C 4.0이다.
- **기준 시나리오를 `plan.baseline_scenario`에 두어** 보기 설정을 바꿔도 새 버전이 생기지 않고, FR-PLAN-04의 "직전 계획 1개"를 소비하지 않는다 (A 투표서가 C 대비 B의 강점으로 지적).

## 6. 병합하지 않은 아이디어와 버린 대안

### 6-1. 1명만 언급해 병합하지 않은 것
- C안: 요청 키를 run·메시지·설명 시도까지 확대(B만), `goal_kind.label_copy_key`(A만), `data_version.content_sha256`(A만), `evaluation_mode`(B만), 철회 세션 정리 인덱스(B만)
- A안: 금리 출처·버전 양방향 CHECK, 시나리오별 ETF 수익률·세금·보수 결과 기록, 고정 필수 파라미터의 타입·범위 (모두 C만)

### 6-2. 버린 대안과 이유
| 대안 | 출처 | 버린 이유 |
|---|---|---|
| 정책 승인 워크플로(draft/approved/retired) + 승인 전 저장 차단 | C | 정책 규칙 13행이 있어야 조건을 저장할 수 있어 TBD-09/17 확정 전에는 동작하지 않는다. B의 `input_field`·`calc_param_key` + 활성화 트리거가 더 가볍게 같은 목적을 이룬다 |
| 전 FK `DEFERRABLE`, 트리거 19개 | C | 스키마 변경마다 PL/pgSQL 함수까지 고쳐야 하고, 쓰기 경로 검증 비용이 크다 |
| 기준 시나리오를 조건 스냅샷의 속성으로 보관 | C | 보기 설정 변경이 새 버전과 적용 이력을 만들어 FR-PLAN-04 "직전 계획"을 소비한다 |
| 월별 점을 행 단위로 저장, 대안마다 전체 계산 행 생성 | A | 30년 목표에서 계산 1회에 1,083행, 비교·대안마다 계산이 늘어 쓰기 증폭이 크다 |
| `calc_parameter_set` 고정 컬럼 | A | CP-03 미결 항목이 늘 때마다 ALTER가 필요하다. B의 키 사전 방식은 데이터 추가로 끝난다 |
| 시나리오 결과를 ETF 0%에서도 항상 3행 저장 | A | 같은 값이 3번 저장된다. 단, 아래 한계 1번의 원인이 된 B의 단순화와 맞바꾼 결정이다 |

## 7. 알려진 한계와 후속 과제

채택안에 남은 약점이다. 투표서에서 확인된 항목이며, 구현 전에 정해야 한다.

1. **ETF 0% 계획에서 기준 시나리오가 GOOD/BAD일 때 결과 행이 없다.** `ck_csr_no_etf`가 AVG 한 행만 허용하므로 기준이 GOOD/BAD이면 기준 시나리오 조인과 대안 FK가 비게 된다(FR-RES-02/09, FR-ALT-01/02). A와 C 투표서가 모두 지적했다. 권장 대응은 ETF 0%에서 기준 시나리오를 AVG 결과로 매핑하는 공통 규칙을 앱에 두고 테스트로 고정하는 것이다. 이 규칙은 최종 스키마에 반영되지 않았다(병합 기준 미충족).
2. **대안 입력 범위의 DB 강제는 비교 오버라이드까지만 있다.** `calc_alternative.changed_value`는 범위 검사가 없어 서비스 검증이 필요하다(CP-02).
3. **ANN 검색 후 필터로 결과 수가 부족할 수 있다.** 운용사 2곳 이상 출처(FR-AI-03)는 게시 직전에 검증한다.
4. **비교·대화 run이 쌓이므로 정리 배치가 필요하다.** 인덱스는 갖췄다.
5. **응답 시간 목표(NFR-PERF-01)는 수치가 정해지지 않아 측정하지 않았다.** 성능 점수는 구조와 쿼리 대응에 대한 평가다.

## 8. 검증

- `final/schema.sql`을 `pgvector/pgvector:pg16` 임시 컨테이너에서 오류 없이 실행했다 (B가 1회, 진행자가 독립적으로 1회). 테이블 25개, 트리거 6개로 일치한다.
- 병합 5건의 제약 시나리오와 사용자 삭제 CASCADE 회귀 시나리오는 `final/erd.md` 끝 '검증 결과'에 있다. 이 시나리오는 작성자(B)가 실행한 결과이며 진행자가 재실행한 것은 스키마 생성까지다.
- 추적표는 SRS 68건 전체를 포함한다 (진행자가 ID 수를 확인).

# ADR-002. 최소 저장 원칙과 토큰 인증 전환

- 상태: 확정 (사용자 지시. 새 토론·투표 없이 진행자가 단독으로 수정)
- 이전: ADR-001의 스키마 (`final/v1/`, 테이블 25개)
- 산출물: `final/schema.sql`, `final/erd.md`, `final/tables.md`, `final/moved-to-code.md` (테이블 14개, 트리거 0개)

## 1. 배경

ADR-001의 채택안은 무결성을 DB에서 최대한 강제했다. 그 결과 다음과 같은 것들이 DB에 들어갔다.
- 바뀔 수 있는 규칙과 코드표: 입력 범위, 경로별 허용 항목, 목표 종류, 파라미터 키
- 다시 계산하면 같은 값이 나오는 결과: 시나리오 결과, 대안, 비교 실행
- 그 둘을 지키는 장치: 트리거 6개, 생성 컬럼 10개, 소유권·종류·복사값 일치용 복합 FK

규칙이 enum, 설정 파일, DB 세 곳에 나뉘고, 결과와 입력이 서로 다른 행에 있어 어긋날 수 있었다. 데모 서비스의 규모에 비해 쓰기 경로가 복잡했다.

## 2. 결정

1. **DB에는 코드로 다시 만들 수 없는 것만 저장한다.**
   - 저장 대상은 세 가지다. 사용자가 만든 원본 데이터, 외부에서 가져온 시점 데이터, 다른 테이블이 참조해야 하는 최소 기록.
   - 나머지는 enum, 설정 파일(`config/rules.yml`, `copy/copy.ko.yml`), 계산 함수, 로그로 옮긴다. 항목별 이동 위치는 `moved-to-code.md`에 있다.
2. **계산 결과를 저장하지 않는다.**
   - `calc_run`은 계획 버전, 기준 데이터 버전 3종, `engine_version`만 기록한다. 결과는 화면을 열 때 다시 계산한다.
   - COMPARE 실행은 저장하지 않는다. CHAT 재계산은 대화 재계산 요청마다 1행 남긴다. 메시지가 참조하지 않는 행은 남을 수 있으며 정리하지 않는다(D-057). 바꾼 값은 `chat_message.condition_changes`에 둔다.
3. **무결성은 PK/FK/NOT NULL/UNIQUE와 단순 CHECK까지만 둔다.**
   - 트리거, 생성 컬럼, 복사값 일치용 복합 FK는 쓰지 않는다.
   - 소유권은 앱이 모든 쿼리에 `member_id` 조건을 붙여 검증한다.
4. **계획 이력은 `plan_version`(INSERT 전용) + `plan.current/previous` + `plan.revision`으로 단순화한다.**
   - 채택 이력 테이블과 멱등 키를 없앤다. 중복 전송과 동시 수정은 `revision` 낙관적 락이 막는다.
5. **인증을 무상태 JWT로 바꾼다.**
   - 만료는 30분이다. 사용자 조작 요청에만 새 토큰을 발급하고(슬라이딩), 폴링에는 발급하지 않는다.
   - 로그아웃은 서버가 처리한다. `POST /api/auth/logout`이 인증 쿠키를 만료시키고 `MemberLoggedOut` 이벤트를 발행하면, chat이 그 회원의 대화를 삭제한다(Y-1). `user_session` 테이블은 삭제한다.
   - NFR-SEC-02 "세션은 서버에서 관리"는 "서버가 토큰 서명과 만료를 검증하고, 만료된 토큰의 요청은 처리하지 않는다"로 재해석한다. 이 재해석은 사용자가 확인했다.
6. **RAG 반정규화는 `chunk_embedding.is_active` 하나만 남긴다.**
   - 부분 HNSW 인덱스의 조건으로 꼭 필요하기 때문이다. 문서 이용 허락 상태는 적재 스크립트가 관리한다.
7. **AI 시도 버전, 질문 입력 경로, 실패 코드, 응답 시간은 로그로 보낸다.**
   - SRS가 버전 기록을 요구하는 곳(NFR-INT-02)은 기준 데이터뿐이다.

## 3. 포기한 것

| 포기한 것 | v1에서 맡던 장치 | 이제 맡는 곳 |
|---|---|---|
| 서버 측 강제 로그아웃·토큰 폐기 | `user_session` 행 삭제 | 없음. 서버 로그아웃은 쿠키를 만료시키므로 브라우저는 토큰을 더 보내지 않지만, 이미 나간 토큰은 남은 만료 시간(최대 30분) 동안 서버에서 그대로 유효하다. 데모 범위에서 수용한다 |
| 다른 사용자 행 참조를 DB가 차단 | `(member_id, id)` 복합 FK | 리포지토리의 `member_id` 조건 |

| 결과의 영속 보관(재계산 없이 조회) | `calc_scenario_result`, `calc_alternative` | `CalcEngine` 재계산 + 앱 캐시 |
| 적용·되돌리기 이벤트의 DB 감사 이력 | `plan_application` + 트리거 | 로그 `plan.changed` |
| 같은 요청의 멱등 처리(같은 응답 재반환) | `request_key` UNIQUE | `revision` 불일치로 0행이면 전체 롤백 + 409 `PLAN_CHANGED`(현재 상태를 싣지 않음) |
| 청크·임베딩 불변 보장 | 불변 트리거 | 적재 스크립트 규칙(필요하면 DB 권한으로 UPDATE 금지) |
| `doc_type`·운용사로 ANN 단계 필터 | 임베딩 행 반정규화 | 조인 후 필터 + `iterative_scan` |
| 데이터 종류 일치(금리 자리에 지수 버전 금지) | 생성 컬럼 + 복합 FK | `DataVersionService.requireKind` |

## 4. 위험과 대응

1. **토큰 탈취 시 로그아웃 후에도 최대 30분간 유효하다.**
   - 대응: 토큰은 HttpOnly·Secure 쿠키로 전달하고, 만료를 30분보다 길게 잡지 않는다.
   - 데모 기간 중 강제 폐기가 필요해지면 서명 키를 교체해 전체 토큰을 무효화한다.
   - 개별 폐기가 필요해지면 폐기 목록(jti, 만료 시각) 테이블을 추가하는 것을 다시 검토한다.
2. **재현성이 엔진의 결정성에 달려 있다.**
   - 계산 로직을 바꾸고 `engine_version`을 올리지 않으면, 과거 AI 설명(FR-AI-02)과 다시 계산한 숫자가 어긋난다.
   - 대응: CI에 고정 입력 회귀 테스트를 둔다. 엔진 코드가 바뀌면 버전 상수를 바꾸도록 검사한다.
3. **앱 검증 누락 시 잘못된 값이 들어갈 수 있다.**
   - DB가 더 이상 범위와 소유권을 막지 않는다.
   - 대응: 모든 쓰기 경로가 `ConditionValidator`와 `member_id` 조건을 거치게 리포지토리·서비스 계층에서 강제한다. 경로별 테스트를 둔다.
4. **결과 조회 비용이 늘어난다.**
   - 결과 화면과 대화 복원이 매번 재계산한다.
   - 대응: (계획 버전, 데이터 버전 3종, engine_version) 키로 앱 메모리 캐시를 둔다. 기준 데이터는 불변이라 무효화가 필요 없다.
   - NFR-PERF-01 목표치(TBD-33)가 정해지면 측정한다.
5. **`is_active` 동기화가 어긋날 수 있다.**
   - 문서와 임베딩의 `is_active`를 FK가 맞춰 주지 않는다.
   - 대응: 같은 트랜잭션에서 함께 갱신한다. 적재 스크립트가 불일치 점검 쿼리를 실행한다.
6. **공시만 찾는 검색의 결과가 부족할 수 있다.**
   - `doc_type` 필터가 ANN 뒤에 걸리기 때문이다.
   - 대응: `iterative_scan`과 운용사 제외 재검색을 쓴다. 부족이 확인되면 `doc_type` 반정규화를 다시 검토한다.
