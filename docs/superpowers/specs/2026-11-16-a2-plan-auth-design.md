# A-2 계획·인증 설계

- 작성일: 2026-11-16
- 담당: A-2 (계획·인증). A팀의 계산·데이터 담당, B팀(AI)과의 경계는 §8
- 근거 문서 우선순위: **A-2 요구사항(xlsx) + 결정사항 DB(Notion CSV) + 이 문서의 결정 > 와이어프레임 > PM 기능정의서 v0.1**
  - 정책(범위·필수 여부·인증·저장)은 앞의 셋을 따른다. 와이어프레임과 기능정의서는 그 문서들이 정하지 않은 화면·흐름의 세부만 가져온다.

## 1. 목적

사용자가 데모 계정으로 로그인해 목돈 목표와 자금 조건을 입력하면, 그 입력을 **내 계획**으로 저장하고 결과 화면으로 보낸다. 결과·대안·비교·대화 화면에서 바꾼 조건은 확인을 거쳐서만 내 계획에 반영되고, 직전 계획 하나로 되돌릴 수 있다.

A-2는 이 흐름의 입구(로그인, 입력, 검증, 저장)와 계획 상태 관리(적용, 되돌리기)를 맡는다. 금액 계산은 하지 않는다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- FR-AUTH-01~03, NFR-SEC-01/02: 데모 계정 로그인, 비로그인 차단, 30분 비활동 만료, 로그아웃
- FR-INP-01~11, CP-02, CP-04: 입력 화면, 항목별 검증, 저장
- FR-PLAN-01~04, 06: 적용 확인, 취소, 적용, 되돌리기, 로그인 후 진입 화면
- FR-RES-05, FR-RES-07: 결과 화면의 내 계획 조건 바, 면책 문구
- 입력 규칙을 계산·대화 쪽도 그대로 쓸 수 있게 제공 (CP-02 "대안·비교·대화로 바꾼 값에도 같은 범위")
- NFR-CMP-01/02, NFR-UI-01: 최신 Chrome 등 데스크톱 기준, 통일된 스타일

**비목표**
- 회원가입, 비밀번호 찾기, 로그인 실패 횟수 제한(TBD-25, PR-02 미채택)
- 모바일 레이아웃(NFR-CMP-02 범위 밖)
- 금액·수익률·기간 계산, 결과 시나리오·그래프·대안·비교·AI 대화 화면 (§8)
- 서버 측 개별 토큰 폐기(ADR-002 §3에서 포기)

**실패 조건** (동작해도 실패로 본다)
- 프론트나 plan 모듈이 금액을 계산해 결과처럼 보여 준다 (NFR-INT-01). 단, 입력 화면의 "월 저축액 자동 초기값"은 단순 나눗셈 입력 보조이며 결과가 아니다(§4.4)
- 화면 문구에 '추천'이 긍정형으로 들어간다 (CP-06, PR-05, TBD-12, TBD-32)
- 입력 범위가 프론트와 백엔드에서 다르게 동작한다
- 비교·대안·대화에서 조건을 바꾸는 것만으로 내 계획이 바뀐다

## 3. 제약

- 백엔드: Java 21, Spring Boot 4.1, Spring Modulith. 모듈 `auth`, `plan`은 `allowedDependencies = {}`. 규칙은 `backend/.claude/rules/*.md`
- 프론트: Vite, React 19, TypeScript strict, Tailwind 4, Vitest. 규칙은 `frontend/CLAUDE.md`, `frontend/.claude/`
- DB: `schema.sql`이 원본, `ddl-auto=validate`. 계산 결과는 저장하지 않는다(ADR-002)
- 로컬 포트: 프론트 5173, 백엔드 8080. CORS 허용 Origin은 `CORS_ALLOWED_ORIGINS`
- 클래스 이름은 `db/moved-to-code.md`를 따른다: `JwtTokenService`, `TokenRenewalFilter`, `@SkipRenewal`, `GoalType`, `InputField`, `ChangePath`, `ConditionValidator`, `PlanInputValidator`, `ConditionOverride`, 이벤트 `PlanChanged`

## 4. 결정 사항

### 4.1 인증

| 항목 | 결정 | 근거 |
|---|---|---|
| 방식 | 무상태 JWT(HS256), 만료 30분 | ADR-002 §2-5, TBD-24 |
| 전달 | **HttpOnly · Secure · SameSite=Lax 쿠키**. 로컬(http)에서는 Secure 끔 | ADR-002 §4-1 |
| 슬라이딩 만료 | `TokenRenewalFilter`가 인증된 요청마다 새 토큰을 쿠키로 다시 발급. 폴링 엔드포인트는 `@SkipRenewal`로 제외 | moved-to-code.md |
| 로그아웃 | `POST /api/auth/logout`이 쿠키를 `Max-Age=0`으로 지움. 토큰 자체는 남은 시간 동안 유효(알려진 위험) | ADR-002 §3 |
| 만료·미인증 | API는 401. 프론트는 401을 받으면 로그인 화면으로 보내고 "다시 로그인해 주세요" 안내 | FR-AUTH-02 |
| 비밀번호 | BCrypt 해시만 저장 | NFR-SEC-01, PR-02 |
| 데모 계정 | 우선 `demo01` 1개. 비밀번호는 로컬 `.env`(`DEMO_ACCOUNTS`)에서 읽어 기동 시 없으면 생성. 저장소에 비밀번호를 두지 않는다. 늘릴 때는 설정에 한 줄 추가 | FR-AUTH-01, 사용자 결정 |
| CSRF | 쿠키 인증이지만 SameSite=Lax + 상태 변경은 POST/PUT만 + JSON 본문만 허용으로 대응. CSRF 토큰은 쓰지 않는다 | 이 문서의 판단(§10) |

배포 시 프론트와 API는 같은 사이트(같은 등록 도메인 또는 CloudFront 하나)로 둔다. 그래야 SameSite 쿠키가 전달된다.

### 4.2 입력 항목과 허용 범위 (CP-02, TBD-09)

금액 단위는 만원, 정수. `rules.yml › input.fields`에 아래 값을 둔다.

| InputField | 필수 | 최소 | 최대 | 비고 |
|---|---|---|---|---|
| `GOAL_TYPE` | 필수 | — | — | 1개만 선택 (FR-INP-01) |
| `GOAL_CUSTOM_NAME` | `CUSTOM`일 때 필수 | 1자 | 100자 | 앞뒤 공백 제거 후 길이. 공백만은 오류 (TBD-09) |
| `GOAL_AMOUNT` | 필수 | 1만원 | 10억원 | (FR-INP-03) |
| `TARGET_PERIOD_MONTHS` | 선택 | 1개월 | 600개월(50년) | 입력은 'n년 n개월', 저장은 개월 (FR-INP-04) |
| `HELD_ASSETS` | 필수 | 0원 | 10억원 | (FR-INP-05, TBD-09) |
| `MONTHLY_SAVING` | 기간이 없으면 필수 | 1만원 | 1,000만원 | '잘 모르겠어요'면 NULL (FR-INP-06) |
| `SAVINGS_RATE_PCT` | 선택 | 0.00% | 50.00% | 소수 둘째 자리. 비우면 NULL(기본금리, §8) (FR-INP-07) |
| `EXISTING_SAVINGS_MONTHLY` | 토글 ON일 때 | 0원 | 1,000만원 | 기존 적금 월 납입액 |
| `EXISTING_ETF_MONTHLY` | 토글 ON일 때 | 0원 | 1,000만원 | 기존 ETF 월 납입액 |
| `SAVINGS_RATIO_PCT` | 아래 4.3 | 0 | 100 | 정수 (TBD-13) |

**항목 간 규칙** (`PlanInputValidator`)
1. **기간과 월 저축액 중 하나는 반드시 있어야 한다.** 둘 다 모르면 "목표 기간 또는 월 저축액 중 하나를 알려주세요." (TBD-14/39 해소, 사용자 결정)
2. 기존 납입액 합계 ≤ 월 저축액 (월 저축액이 있을 때). 월 저축액이 없으면 이 비교는 하지 않는다.
3. 토글 ON인데 두 납입액 합계가 0이면 토글 OFF로 처리한다 (TBD-13).
4. 보유 자산 ≥ 목표 금액은 **오류가 아니다**. 저장하고 결과 화면이 '이미 목표를 넘었어요'(CF-03, TBD-34)를 보여 준다.

같은 범위가 대안·비교·대화 경로에도 적용된다. `ConditionValidator.validate(path, values)`가 공통 검사한다. 경로별로 바꿀 수 있는 항목(`rules.yml › change-paths`)의 초기값은 와이어프레임의 "바꿀 수 있는 조건"을 따른다. 계산 담당과 B팀이 이후 조정한다.

| ChangePath | 바꿀 수 있는 항목 | 최대 개수 |
|---|---|---|
| `INPUT_EDIT` | 전체 | 제한 없음 |
| `ALTERNATIVE` | 월 저축액, 기간, 비중 | 1 |
| `COMPARE` | 월 저축액, 기간, 비중, 적금 금리 | 4 (TBD-35) |
| `CHAT` | 월 저축액, 기간, 비중, 적금 금리 | 4 |

### 4.3 기존 저축과 비중 (FR-INP-08, CF-08)

1. **기준 비중**은 적금 50 : ETF 50 고정 (`calc_param.DEFAULT_SAVINGS_RATIO`, TBD-13)
2. 월 저축액을 비중대로 나눠 보여 준다. 예: 100만원 → 적금 50만원, ETF 50만원
3. 토글 ON이고 납입액 합계 > 0이면 입력 화면에서 두 선택지 중 하나를 고른다(기본 선택 없음, 필수)
   - **A. 기준 비중으로 맞추기** → 50:50
   - **B. 지금 비중 유지** → 적금 납입액 ÷ 합계, 정수 반올림. 예: 100:20 → 83:17
4. 토글 OFF → 50:50

| 경우 | `savings_ratio_pct` 저장값 |
|---|---|
| 토글 OFF, 또는 A 선택 | NULL (계산 쪽이 기준 비중 사용) |
| B 선택 | 계산된 정수 비중 |

- 화면 문구는 '기준 비중', '지금 비중'을 쓴다. '추천'은 쓰지 않는다.
- CF-08은 결정사항 DB에 '팀 회의로 확정 필요'로 남아 있다. 이 안을 회의 안건으로 올린다.

### 4.4 목표 종류와 입력 보조 (기능정의서에서 가져옴)

`GoalType` 선언 순서 = 화면 순서. 표시명은 `copy.ko.yml › goal.<CODE>`.

| GoalType | 표시명 | 기본 목표 금액 | 기본 기간 |
|---|---|---:|---:|
| `JEONSE` | 전세자금 | 10,000만원 | 24개월 |
| `WEDDING` | 결혼자금 | 3,000만원 | 12개월 |
| `INDEPENDENCE` | 독립자금 | 3,000만원 | 36개월 |
| `TRAVEL` | 여행자금 | 200만원 | 6개월 |
| `CUSTOM` | 직접 입력 | 직전 값 유지 | 직전 값 유지 |

- 기본값은 `rules.yml › goal-defaults`에 두고 입력 규칙 API로 내려 준다.
- 목표 칩을 바꾸면 금액·기간을 기본값으로 바꾸고 보유 자산은 유지한다.
- 기간 프리셋 버튼: 3·6·12·24·36개월 + 직접 입력('n년 n개월').
- **월 저축액 자동 초기값**: `floor(max(목표 − 보유, 0) ÷ 기간)` (만원 단위 내림). 기간이 있고 사용자가 직접 고치기 전까지만 자동 갱신. 허용 범위 밖이면 범위로 맞춤(0 → 1만원이 아니라 비워 둠, 1,000만원 초과 → 1,000만원). 이 값은 이자·수익을 반영하지 않은 입력 보조라고 도움말에 쓴다.

### 4.5 계획 저장·적용·되돌리기

| 동작 | 결정 | 근거 |
|---|---|---|
| 결과 보기 | 검증 통과 → `plan_version(source=INPUT)` INSERT → `plan.current` 갱신 → 결과 화면 이동 | FR-INP-10, TBD-21 |
| 계산 시작 월 | `calc_start_month`는 **처음 저장한 달**로 고정. 이후 입력 수정·적용에서도 유지 | TBD-38 |
| 기준 시나리오 | 첫 저장 시 `plan.baseline_scenario = AVG`. 이후 변경은 결과 화면(계산 담당)이 적용 API로 요청 | TBD-40 |
| 적용 | 비교·대안·대화의 변경값 + 확인 시점의 `revision`을 보냄 → 검증 → 새 `plan_version(source=ALTERNATIVE/COMPARE/CHAT)` → `previous = 이전 current` | FR-PLAN-01, 03 |
| 취소 | 서버 호출 없음 | FR-PLAN-02 |
| 되돌리기 | `current ↔ previous` 교환이 아니라 `current = previous, previous = NULL`. 직전 1개까지만 | FR-PLAN-04, TBD-22 |
| 동시 수정 | `revision` 불일치면 409 + 현재 계획 반환. 프론트는 "그사이 계획이 바뀌었어요" 안내 후 화면 갱신 | PR-08 (이미 설계된 낙관적 락) |
| 중복 클릭 | 요청 중 버튼 비활성화. 서버는 revision으로 두 번째 요청을 거절 | TBD-37 |
| 이벤트 | 저장·적용·되돌리기 커밋 시 `PlanChanged` 발행 | modulith.md |
| 로그인 후 진입 | 계획 있음 → 결과 화면 + "demo01 님, 지난번 적용한 계획이에요" / 없음 → 빈 입력 화면 | FR-PLAN-06, 와이어프레임 S8 |
| 입력 수정 진입 | 현재 계획 값을 채워서 연다. 월 저축액도 저장값 그대로(자동 초기값으로 덮지 않음) | FR-INP-11 |

### 4.6 표시 형식 (CP-04)

프론트 `format` 유틸 하나에 모은다. 계산하지 않고 받은 숫자의 모양만 바꾼다.

| 대상 | 형식 | 예 |
|---|---|---|
| 금액 | '약 N만원', 천원 단위 반올림 후 만원 표시, 천 단위 쉼표. 1억 이상도 만원 단위 | 약 4,980만원 / 약 12,000만원 |
| 목표 대비 | 부호 + 달성/미달 라벨. 0원은 '달성' | +150만원 달성 / −20만원 미달 |
| 기간 | 'n년 n개월'. 0인 쪽 생략 | 3년 / 1년 6개월 / 8개월 |
| 비중 | '적금 a : ETF b' 정수 | 적금 83 : ETF 17 |

억 단위 표기("1억 2,000만원")는 와이어프레임에 없어 쓰지 않는다. 판정에 반올림 전 값을 쓰는 것은 계산 쪽 결정(TBD-16).

### 4.7 화면 (와이어프레임 01, 02, 03 상단·하단, 04 S1·S5·S7·S8)

**공통 헤더**: 왼쪽 서비스명, 오른쪽 `demo01 님 · 로그아웃` (FR-AUTH-03).

**01 로그인**
```
목돈 플래너
로그인하면 내 목표와 계획을 이어서 볼 수 있어요.
[아이디        ]
[비밀번호      ]
[    로그인    ]
로그인하지 않으면 입력 화면과 결과 화면에 들어갈 수 없어요.
```
실패 시 "아이디 또는 비밀번호를 확인해 주세요." 와이어프레임의 '데모 계정 demo / ••••' 표시는 넣지 않는다(계정을 별도 전달).

**02 입력** — 목표 칩을 고르면 아래 섹션이 순서대로 열린다(FR-INP-01).
```
1. 목표          [전세자금][결혼자금][독립자금][여행자금][+ 직접 입력]
2. 목표 금액*    [ 5,000 ]만원        지금 이 목표에 쓸 수 있는 돈* [ 600 ]만원
   목표 기간이 정해져 있나요?  (●정해져 있어요 ○아직 없어요)
   [3개월][6개월][1년][2년][3년]  또는 [ n ]년 [ n ]개월
3. 매달 저축할 수 있는 금액을 알고 있나요? (●알아요 ○잘 모르겠어요)
   [ 120 ]만원   기준 비중이면 적금 60만원 · ETF 60만원
4. 적금 금리 (연, 세전)  [    ]%  비워 두면 은행연합회 전월 평균금리 적용
5. [토글] 이미 저축 중이에요
   적금 [100]만원  ETF [20]만원
   (○기준 비중으로 맞추기 50:50  ○지금 비중 유지 83:17)
                                  [결과 보기]
```
오류(S1): "결과 보기"에서 검증 → 칸마다 빨간 테두리 + 안내, 상단에 "확인이 필요한 항목이 N개 있어요.", 첫 오류 칸으로 스크롤과 포커스.

**03 결과 화면 중 A-2 부분**
- 상단 조건 바(FR-RES-05): `내 계획 전세자금 · 목표 5,000만원 · 3년 (2029.11) · 보유 600만원 · 월 120만원 · 적금 금리 3.2% · 적금 83 : ETF 17 [입력 수정]`. 금리를 비웠으면 계산 쪽이 돌려준 적용 금리를 쓰고 '(기본)'을 붙인다. 기간이 없으면 '기간 미정'.
- 하단 면책 문구(FR-RES-07, 격식체, 모든 결과 화면 하단 고정):
  > 본 결과는 입력하신 조건과 과거 데이터를 바탕으로 한 모의 계산이며, 실제 수령액이나 수익을 보장하지 않습니다. 특정 금융상품의 가입을 권유하지 않으며, 환율 변동은 반영하지 않았습니다. 투자 결정은 본인의 판단과 책임하에 이루어져야 합니다.
- 적용 확인 모달(S7)과 적용 토스트·되돌리기(S8): 공용 컴포넌트로 만들어 대안·비교·대화 화면에 제공한다.

**디자인 기준(NFR-UI-01)**: 와이어프레임이 흑백 초안이라 색·서체는 A-2가 정한다. Tailwind 테마 토큰(색, 간격, 글자 크기)과 공통 컴포넌트(버튼, 칩, 라디오, 토글, 입력+단위, 도움말, 오류 문구, 모달, 토스트)를 `frontend/src/components/ui`에 두고 다른 화면도 이것을 쓴다.

**문구**: 고정 문구는 프론트·AI 공용 문구표 파일 하나(`copy.ko.yml`)에서 관리한다(TBD-32). 해요체, 면책만 격식체.

## 5. 접근 방식 (입력 규칙 공유)

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **(가) 채택** | 백엔드 `rules.yml`이 원본. `GET /api/input-rules`로 범위·필수·단위·목표 기본값을 내려 주고 프론트가 그 값으로 검증 | 원본 하나, 값 변경 시 한 곳만 수정 | 화면 진입 시 요청 1회 추가 |
| (나) | 프론트에 같은 상수를 한 번 더 작성 | 가장 빠름 | 값이 어긋날 위험 |
| (다) | 빌드 시 `rules.yml`에서 프론트 상수 생성 | 어긋나지 않음 | 빌드 단계 추가, 현재 규모에 과함 |

사용자가 (가)를 골랐다. 서버 검증이 최종 기준이고, 프론트 검증은 즉시 안내용이다. 두 검증 모두 같은 응답 값을 쓰므로 오류 문구 키도 서버 응답의 필드 코드와 맞춘다.

## 6. API (A-2 제공)

모든 경로는 `/api` 아래. 오류 본문은 RFC 9457 `ProblemDetail` + `errors: [{field, code}]`.

| 메서드 | 경로 | 인증 | 설명 |
|---|---|---|---|
| POST | `/api/auth/login` | 없음 | `{loginId, password}` → 쿠키 발급, `{loginId, hasPlan}` |
| POST | `/api/auth/logout` | 필요 | 쿠키 삭제 |
| GET | `/api/auth/me` | 필요 | `{loginId, hasPlan}`. 새로고침 시 로그인 상태 확인 |
| GET | `/api/input-rules` | 필요 | 항목별 `{required, min, max, unit, scale}`, 목표 종류와 기본값, 기간 프리셋, 기준 비중 |
| GET | `/api/plan` | 필요 | 현재 계획 값 + `revision` + `canUndo`. 없으면 404 |
| POST | `/api/plan` | 필요 | 입력 화면 저장(source=INPUT). 검증 오류 400 |
| POST | `/api/plan/apply` | 필요 | `{source, changes, expectedRevision}`. 검증 오류 400, revision 불일치 409 |
| POST | `/api/plan/undo` | 필요 | `{expectedRevision}`. 되돌릴 계획 없으면 409 |

`memberId`는 JWT subject에서만 얻는다. 응답 JSON은 camelCase. REST Docs로 문서화해 `openapi3.yaml`에 포함한다.

## 7. DB 변경

1. `plan_version.goal_custom_name`: `VARCHAR(50)` → `VARCHAR(100)` (TBD-09)
2. `plan_version.existing_monthly_contribution` → **`existing_savings_monthly`, `existing_etf_monthly` 두 컬럼**으로 나눈다. 입력 수정 화면에 두 값을 되살려야 해서다(FR-INP-11). 둘 다 NULL = 토글 OFF.
3. 변경 후 `db/tables.md`, `db/erd.md`, `db/moved-to-code.md`의 해당 줄도 고친다.

2번은 계산 쪽 `RatioResolver`가 읽는 컬럼이라 계산 담당과 맞춘 뒤 반영한다(§8).

## 8. 다른 담당과의 경계

| 상대 | A-2가 제공 | A-2가 받음 | 맞출 것 |
|---|---|---|---|
| A팀 계산·데이터 | `PlanChanged` 이벤트, `plan_version` 값, `ConditionValidator`, 적용 API, 조건 바·면책·적용 모달·토스트 컴포넌트, UI 공통 컴포넌트 | 결과 화면 데이터 API(시나리오, 적용 금리 등), 기본금리 데이터, `DEFAULT_SAVINGS_RATIO` | 결과 화면 페이지 소유자(조건 바·면책을 끼울 위치), 기간 없음 + 월 저축액만 있을 때 결과 형식(TBD-11), §7-2 컬럼 변경 |
| B팀 AI | `ConditionValidator`(대화로 바꾼 값 검증), 적용 API(대화의 '내 계획으로 적용') | — | `rules.yml › change-paths.CHAT` 항목 |

**결과 화면 라우트**: A-2가 `/result` 페이지 뼈대(헤더, 상단 조건 바, 본문 자리, 하단 면책 문구)를 만들고, 본문은 계산 담당이 채운다. 결과 데이터 API가 준비되기 전에는 조건 바와 면책 문구를 `GET /api/plan`만으로 그린다. 적용 금리 '(기본)' 값만 나중에 붙인다.

**문구표**: `copy/copy.ko.yml`(저장소 루트)을 프론트·AI가 같이 쓴다. 아직 없으므로 A-2가 처음 만들고 자기 문구를 넣는다.

## 9. 테스트

- 백엔드: `PlanInputValidator`·`ConditionValidator` 경계값 단위 테스트(각 항목 최소−1, 최소, 최대, 최대+1, 항목 간 규칙 4개), 로그인·만료·갱신·로그아웃·401 슬라이스 테스트, 적용·되돌리기·revision 충돌 통합 테스트(Testcontainers), `ModularityTests`
- 프론트: `format` 유틸, 월 저축액 초기값, 비중 계산(B안 반올림), 입력 화면 분기(칩 → 섹션 열림, 라디오 분기, 토글), 오류 요약·첫 오류 포커스, 401 → 로그인 이동
- 수동: 로그인 → 입력 → 결과 → 입력 수정 → 저장값 유지, 30분 만료

## 10. 이 문서에서 내가 정한 것 (확인 필요)

- 쿠키 SameSite=Lax + CSRF 토큰 없음
- 데모 계정 비밀번호를 `.env`에서 읽어 기동 시 생성
- 기존 저축 입력을 적금·ETF 두 칸으로 받고 DB 컬럼을 둘로 나눔
- B안(지금 비중 유지) 비중은 적금 ÷ 합계를 정수 반올림
- 비중 선택(A/B)은 기본 선택 없이 필수
- 월 저축액 자동 초기값이 0이면 비워 둠
- 되돌리기 후 `previous = NULL`(다시 되돌리기 불가)
- 금액은 1억 이상도 만원 단위 표기
- 로그인 화면에 데모 계정 정보를 표시하지 않음
- 디자인 토큰과 공통 컴포넌트를 A-2가 만들어 공유
- 경로별 바꿀 수 있는 항목의 초기값(§4.2 표)
- `/result` 페이지 뼈대를 A-2가 만들고 본문은 계산 담당이 채움
- 문구표 `copy/copy.ko.yml`을 A-2가 처음 만듦
